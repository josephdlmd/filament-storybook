# UI rules and their basis

Every rule the patterns, `storybook-instructions`, `storybook-test` and `storybook-audit` apply is listed here with its evidence. Every rule was re-checked against the live sources on 2026-10-11.

**Base: the Carbon Design System.** IBM's system for enterprise products, whose guidance covers the data tables, filters, forms, dialogs and notifications these apps are made of. A rule that follows Carbon needs no further evidence.
- **Form wording and errors follow GOV.UK,** whose user research on hints, placeholders and error messages is the strongest available.
- **WCAG 2.2 AA always wins;** it is the accessibility floor.
- **Where Carbon is silent,** a rule needs its own current evidence: W3C WAI, USWDS, NIST SP 800-63B-4 for sign-in, or research from about 2022 on, such as NN/g. Where we depart from Carbon, the rule says why (see "Where we differ from Carbon").
- **Real-app references (Mobbin) and preference never justify a rule.** Formats follow the app's locale, not GOV.UK's UK style guide.
- Carbon's guidance on usage and behaviour is adopted, not its look; apps keep their Filament theme. **In a compact app, sizes, spacing and text weights follow Carbon's specifications too** wherever Filament differs (owner, 2026-10-11: "Filament looks so big"; weights added the same day); colours, typefaces, corner radii and icons stay the theme's, and no Carbon code or CSS is installed.
- **Writing guidance Carbon took down** (2026-09-30) may be sourced from IBM Accessibility's content design pages (ibm.com/able, public), accepted by the owner on 2026-10-11.
- **Business facts come from the owner,** such as the TIN format and decimal places. They don't need research. They're listed under "Business standards" and built into the patterns.

Dates in brackets are the "updated" dates the pages showed when checked. On 2026-09-30 Carbon moved to a new site; its content guidelines (writing style and action labels) were taken down and now point to IBM Style, which needs a sign-in. Rules cite the live component and pattern pages, which carry their own content rules, and cite the archived `carbon-website` snapshot (2026-09-30) only where no live page covers a rule.

## Forms

- **Labels are visible and above their fields; no `hiddenLabel()`.** In a line-item table the column header is the visible label (see Line items). Carbon forms (Aug 2026): "Top-aligned labels are Carbon's default" and "Every text input should have a descriptive and visible label". *Audit.*
- **No `placeholder()`; an example goes in `helperText()` as "For example, …".** USWDS text input (Aug 2026: "Avoid placeholder text"); GOV.UK text input (Jun 2026: no placeholder "for hints or examples"); hints worded "For example, …" in GOV.UK's dates and National Insurance number patterns and USWDS input mask. *Audit, test.*
- **Helper text is one short line without a full stop, only where the label isn't enough, and has no links.** Carbon forms (Aug 2026): "Only use helper text when truly necessary" and it "should not run longer than the input area"; GOV.UK text input (Jun 2026): "a single short sentence, without any full stops", and no links in hint text. *Audit.*
- **Each input is about as wide as its answer.** Carbon forms (Aug 2026): "The field widths should reflect the intended length of the content"; USWDS text input (Aug 2026). *Pattern `forms-money-input`.*
- **A value with a known shape (TIN) is one field, and accepts spaces, dashes and dots.** It is stored in the owner's format (see Business standards). USWDS text input (Aug 2026): "Avoid breaking numbers with distinct sections … into separate input fields"; W3C WAI forms tutorial: "Be forgiving of different input formats". **No input masks:** the one mask a qualifying source has tested, USWDS's, failed WCAG 2.1 AA (Apr 2025: recovering from an error is difficult), and WCAG wins. USWDS itself still offers masks for fixed formats. *Pattern `forms-tin`.*
- **An email address is one `type="email"` field, with spellcheck off, up to 254 characters and wide enough to show about 30; it is typed once, never twice to confirm.** GOV.UK email addresses (2026: "Only do this if your user research shows it to be effective"; "make sure you can see at least 30 characters at once"). The error says "Enter an email address in the correct format, like name@example.com" (house default). *Audit (an email field that isn't `email()`), pattern `forms-contact-details`.*
- **A phone number is one `type="tel"` field, phone-number-sized, that accepts it in whatever format the user knows:** spaces, hyphens, dashes, brackets, with or without the country code. GOV.UK telephone numbers (2026: "Let users enter phone numbers in whatever format is familiar to them"; "Allow for additional spaces, hyphens, dashes and brackets, and be able to accommodate country and area codes"); GOV.UK text input ("phone number inputs should be phone number-sized"). It is stored in the owner's format (see Business standards). *Audit (a phone field that isn't `tel()`), pattern `forms-contact-details.phone`.*
- **An address is separate fields, one per part, each as wide as its content, with only the parts really needed required,** because every address the apps take is Philippine; one text box only where addresses come from any country. GOV.UK addresses (2026: multiple inputs only when you "know which countries the addresses will come from" and "can find a format that supports them all"; "only make individual text inputs mandatory if you really need the information"). *Pattern `forms-contact-details.address`.*
- **A unit shown before or after a field (₱, kg, %) is part of the field's name for screen readers, and a unit the user types too is accepted, not refused.** GOV.UK text input (2026: "Do not rely on prefixes or suffixes alone, because screen readers will not read them out"; "Allow for this in your validation and do not show an error"). The house script adds the unit after the label ("Discount, %"). *House script, pattern `forms-percentage`.*
- **One choice from up to five options: radios. More than five: a searchable select.** Carbon forms (Aug 2026): "When you have more than five options to present to the user, use a select list"; USWDS select (Aug 2026: a select is the "UI of last resort"). *Pattern `forms-choice`.* Options are stacked, never side by side; in alphabetical or increasing order, or the most used first; each of three words or fewer, with any detail in `descriptions()` (a record's name may be longer). An optional radio group has a "None" option, since a picked radio can't be cleared; otherwise it is required. Carbon forms and checkbox (Sep 2026: groups arranged "vertically"); Carbon select (Sep 2026: "alphabetical order or in increasing order"); Carbon dropdown (Sep 2026: option text "should not exceed three words"); Carbon radio button (Sep 2026: "an 'other' or 'none' option"). *Audit, test.*
- **Several choices from up to five options: a checkbox list. More than five: a multiple select, searchable when the list is long.** Carbon forms (Aug 2026: more than five options, "use a select list (combo box or multiselect)"); Carbon dropdown (Sep 2026: filtering for a long list).
- **Free-text tags (`TagsInput`) only for labels the user makes up; known choices are a multiple select.** Users' own tag names may be long; Carbon's 20 characters is for titles the author writes. Carbon tag (Sep 2026: "Use for creating user-generated custom labeling"; long titles only "when there are user-defined names that cannot be controlled"); Carbon dropdown (Sep 2026: "Use a multiselect when the user needs to select multiple options from a list of predefined options").
- **No rich-text or Markdown editor for now; a `Textarea` instead.** In Filament 5 neither editor's toolbar can be reached by keyboard: every button is `tabindex="-1"`, with no arrow keys (checked 2026-10-11: 0 of 20 and 0 of 13 buttons; Filament's source says the keyboard pattern isn't built yet). When it is, an editor offers only the tools its content needs, with tooltips on hover and focus. WCAG 2.1.1; Carbon text toolbar (Aug 2026: "adding or removing icon buttons based on specific user needs"; "Tab and Shift + Tab move focus in and out of the toolbar"). *Audit.*
- **A yes/no saved with the form is a `Checkbox` with a positive label. A `Toggle` is only for something that applies at once (a `ToggleColumn`).** Carbon checkbox and toggle (Sep 2026); NN/g checkboxes (Jun 2024). *Audit, pattern `forms-yes-or-no`.*
- **A toggle in a table shows a tick when on, and its label names the setting and never changes with it.** Carbon toggle (Sep 2026, accessibility: a tickmark so state is clear "without relying on use of color"; "The label's text should not change based on its state"). *House defaults (`ToggleColumn` tick).*
- **No slider for amounts, dates or wide ranges; where one is used, the value can also be typed.** Carbon slider (Sep 2026: "Do not use for extremely large ranges"; accessibility: "Users can also directly enter a value").
- **A 12-hour time shows AM or PM in capitals, without full stops.** Carbon date picker (Sep 2026).
- **Defaults only where most people would pick that value anyway and a missed change causes no error. Checkboxes start unchecked; consent, legal and opt-in boxes are never pre-checked.** Carbon forms (Aug 2026) and checkbox (Sep 2026); NN/g checkboxes (Jun 2024: pre-checked opt-ins are "a deceptive pattern").
- **What the user already entered in the same task isn't asked again:** it is filled in, or offered to pick (a delivery address "Same as billing", the customer carried from an order to its invoice), unless it must be typed again for security or has changed. WCAG 3.3.7 (Understanding, Sep 2025: "auto-populated, or available for the user to select"). *Pattern `forms-form-container.wizard`.*
- **Fields about the user say what they hold** (`autocomplete` `name`, `email`, `username`, `current-password`, `new-password`), so the browser can fill them in; fields about anyone else don't, or the browser would offer the user's own email for a supplier. WCAG 1.3.5 (Understanding, Sep 2026: "specifically scoped to inputs collecting information about the user"); WCAG 2.2 §7 input purposes. Filament gives its log in email "on" and its sign-up and profile name and email nothing. *House defaults (Filament's account pages).*
- **Dates can always be typed, never through a picker whose text box is read-only; set min and max dates where the range is limited.** In Filament that means the native `DatePicker`, never `native(false)`, whose JavaScript picker has a read-only text box. Carbon date picker (Sep 2026): "There should always be a simple way to enter dates in a text field" and "Use min and max dates"; USWDS date picker (Aug 2026): "Always allow a user to type in the date manually". *Audit, pattern `forms-date`.*
- **Uploads state their limits up front:** accepted types, maximum size, and a helper text such as "PDF or JPG, up to 10 MB". USWDS file input (Aug 2026); Carbon file uploader; Filament docs (always set accepted types). The drop zone says both ways to add a file, in sentence case ("Drag and drop a file here or click to upload"), in place of FilePond's "Drag & Drop your files or Browse" (Carbon file uploader *(archived)*: "describe that you can either drag and drop a file into the drop zone or click on the button"). *Audit, house default (the drop zone), pattern `forms-file-upload`.*
- **An upload of several files goes in a slide-over or on a page, never in a modal, and an upload's error says what is wrong in GOV.UK's words** ("The selected file must be a PDF or JPG", "The selected file must be smaller than 10 MB"); FilePond's own messages in the browser are in Filament's bundled script and can't be reworded. Carbon file uploader (Sep 2026: "Do not use upload in a modal when multiple files are uploaded"; errors "provide clear guidance to help the user resolve the error"); GOV.UK file upload (error messages). *Pattern `forms-file-upload`.*
- **Leaving a form with unsaved changes asks first.** Carbon global header (Aug 2026: "If state or progress will be lost, inform users of this consequence"). *House defaults (`unsavedChangesAlerts()`).*
- **Optional fields say "(optional)"; required ones carry no mark,** one convention throughout the app. Filament's asterisk is off app-wide; a required input keeps its `required` attribute, and a required radio group `aria-required`, so screen readers still say it. Carbon form (Sep 2026: "The pattern used should be consistent throughout your product"; radio button accessibility: required groups "identified programmatically"). Decided by the owner on 2026-10-11, in place of marking the smaller group. *House defaults, audit, test.*
- **The browser's own validation is off,** so a form's errors are the app's, worded as below, never the browser's "Please fill out this field." GOV.UK validation ("Turn off HTML5 validation"); Carbon number input (Sep 2026, accessibility: the browser "simply prevents the typing … without explanation"). *House defaults.*
- **Amounts, quantities and costs are text inputs with a numeric keypad,** never `type="number"`, which steps, rounds and silently refuses what is typed; the server checks the number. Carbon number input (Sep 2026: "avoid number input for continuous variables such as prices, distances, lengths"); GOV.UK text input (numbers). *House defaults.*
- **Limits are stated before the user types:** a range or a number of decimal places ("Up to 3 decimal places"), a maximum length ("Up to 500 characters"), a new password's minimum length. Carbon number input (Sep 2026, accessibility: "Notify users of allowable input ranges through helper text"); Carbon text input (Sep 2026: "helper text listing any requirements related to the data format"). *Patterns `forms-quantity`, `forms-unit-cost`.*
- **One column; fields sit side by side only when they belong together,** such as a date range's From and To. Save and Cancel stay at the bottom, never in the header; the first field takes focus; many optional fields go in a section of their own. Carbon forms (Aug 2026: "Carbon generally recommends single-column forms"; "Do not top align primary and secondary action buttons"; the first required input "should receive focus"; "devoting an entire section to optional fields"); Carbon date picker (Sep 2026: range inputs labelled "with a start and end label"). Filament gives a resource's form and view two columns unless the form sets its own, so a house default makes every top-level schema one column; sections, grids and fieldsets keep theirs. *House default, audit (a form set to several columns), patterns `forms-record-form`, `forms-date.range`.*
- **Error messages say what to do, using the field's label:** "Enter the TIN", "Select payment terms". No "invalid", "is required", "please" or "sorry", and what the user typed stays. GOV.UK error message (Jan 2024); NN/g error messages (May 2023); WCAG 3.3.1 and 3.3.3. An error is at most two lines (Carbon common actions, Aug 2026: "no longer than two lines"). The house defaults word Laravel's errors with GOV.UK's templates (text input, Jun 2026; date input, Jul 2026): "Enter TIN", "Credit limit must be a number", "… must be a whole number", "… must be 0 or more", "… must be 50 characters or less", "… must be a real date", "… must be the same as or after …", and "Enter … in the correct format" for a format (GOV.UK error message, Jan 2024: "Enter a National Insurance number in the correct format"). A number's upper limit says "or less", as GOV.UK's error message page does for a length, since these are mostly amounts; GOV.UK's text input template says "or fewer". They are Laravel's lines, not each field's, so a field that sets a message of its own keeps them for its other rules, and a field is named by its label as written ("TIN"), without "(optional)". *Audit, house defaults.*
- **Validate on submit, or when the user leaves a field they have changed; never while they type, and never flag an untouched empty field.** Carbon forms (Aug 2026: as soon as the field loses focus); USWDS text input (Aug 2026: only after the user "has interacted with a particular field"); NN/g hostile errors (Oct 2022); NN/g error messages (May 2023).
- **A short form may disable its primary button until its requirements are met; a long form never does.** Every form disables it while submitting. Hide what the user may not do. A temporarily unavailable action stays visible, with text saying why and how to make it available; a tooltip on a disabled button alone can't be reached by keyboard. Carbon forms and disabled states (Aug 2026); USWDS button (Oct 2024): "Explain why an action is unavailable and how to make it available".

### Line items

Pattern `forms-line-items`. Checked against the live sources on 2026-10-10.

- **Line items are a table repeater: one column per field, and every field keeps its label.** On a wide screen the column header is the visible label and the field's own label stays for screen readers; on a narrow screen the rows stack and each label shows above its field. No `hiddenLabel()` on a cell field, because the header disappears when rows stack. Filament removes the cell labels with `display: none` once headers show, which leaves every field unnamed, so the house CSS hides them on screen only. WCAG 1.3.1, 3.3.2 (updated Mar 2026) and 4.1.2; W3C WAI forms tutorial (May 2024): a label may be hidden on screen when the context makes the purpose clear, "though it still needs to be provided within the code". *House CSS; test and audit (axe), audit (`hiddenLabel()`).*
- **Each column header is its field's label, word for word,** so what screen-reader and voice-control users hear matches what is on screen. A field without a column isn't shown at all. WCAG 2.5.3 (Apr 2026). *Audit.*
- **A worked-out value in a row, such as the line total, is read-only text, not a disabled field.** Disabled fields aren't read by screen readers and needn't meet contrast. It is worked out again on the server when saving, never taken from the form. Carbon text input (Sep 2026); see also "Hidden fields" under engineering rules.
- **Numbers in a line are right-aligned, with each column about as wide as its answer.** USWDS table (Aug 2026); Carbon forms and USWDS text input (Aug 2026).
- **Lines that can be reordered also move with buttons, not only by dragging;** if the order doesn't matter, reordering is off. Filament's repeaters reorder by dragging alone by default. WCAG 2.5.7 (Aug 2026). *Audit.*
- **A line with more fields than fit without truncation is not a table row:** each line becomes a small form with its labels on screen. Carbon data table (Sep 2026): not for "a more complex display of the data or interactions", and not where information "can feel cramped or needs truncation". No source sets a field count or numbering. *Pattern `forms-line-items.longRow`.*

## Feedback and dialogs

- **Confirm destructive or irreversible actions in a danger dialog, and don't confirm routine ones.** The title repeats the label of the action that opened it, the description says the consequence (never Filament's "Are you sure you would like to do this?"): what else goes and that it can't be undone, or, for a soft delete that can be restored, how to get it back. The confirm button uses the same verb. Carbon dialogs (Aug 2026) and modal (Sep 2026: "use the button label for the modal title"); Carbon common actions (Aug 2026: low-impact deletes need no confirmation); WCAG 3.3.4 (changes to data are reversible, checked or confirmed). A delete that also destroys other records asks the user to type the record's name first, and a delete that fails says so in a notification. Carbon common actions (Aug 2026: "have the user type the name of the resource they are deleting"; "If the deletion fails, raise a notification"). A danger confirmation focuses Cancel and any other confirmation its primary button (Carbon modal: "For destructive interactions, the 'cancel' button takes focus"; otherwise "the primary button takes focus"). *Audit, pattern `actions-delete` (`withTypedName`), house defaults (focus).*
- **A record used on a posted document is archived, never deleted; one never used can be deleted for good.** Archive is gray with no confirmation, since Restore undoes it, and ends with a toast; an "Archived" filter shows archived records; Delete for an unused record confirms in a danger dialog. In Filament, archiving is a soft delete. Carbon common actions (Aug 2026: delete "destroys an object"; confirm when "the data cannot be recreated easily"; low-impact actions need no confirmation); Carbon button (danger only for destructive actions); the business standards (records kept five years; archive or delete, 2026-10-12). *Pattern `actions-archive`.*
- **Danger emphasis matches the action's place:** a delete among other actions is low-emphasis danger (tertiary, which Filament calls outlined, or ghost, a link); the button that confirms it is solid danger. Danger buttons always have a text label. Carbon button (Sep 2026). *Audit, house defaults.*
- **Buttons say what they do with a verb, and its object where it helps ("Delete order", "New supplier"); never OK, Yes, Done, Submit or Confirm,** except a message that only needs acknowledging. A common action (Add, Edit, Delete, Cancel) may stand alone; a noun alone is never a label. A modal's title and confirm button repeat the label of the button that opened it. Carbon button (Sep 2026: "use the {verb} + {noun} content formula on buttons except in the case of common actions"; "Do not use only a noun as a button label"); Carbon modal (Sep 2026: "Avoid vague or passive words, such as Done or OK"; "if the icon name is New user, use New user as the modal title, not Create user"); Carbon forms (Aug 2026: "Abstract terms like "Submit" give the user the impression that the form is generic"); USWDS button ("Lead with a verb"). *Audit, test, house defaults (the confirm button repeats the action's label, or is "Save" for an "Edit …" form; the New modal is titled "New …").*
- **Two empty states.** With nothing yet, say what goes here and offer the next step. When nothing matches a search or filter, say so and suggest adjusting them. The heading is short and, where it can be, positive ("No suppliers yet", "Start by adding suppliers"); the description says the next step. An empty state offers one action, and it is outlined when the page already has a primary button. Carbon empty states (Aug 2026: "Don't cover multiple options in one empty state"; "using a tertiary button for the call to action"); Carbon button (Sep 2026: "a tertiary button is the ideal solution"). *Audit, pattern `tables-list-table`.*
- **A modal with buttons (a form or a confirmation) closes only by its buttons, its × or Esc, never by a click outside it,** so a stray click loses nothing. A modal with nothing to submit, such as View, may also close by a click outside. Carbon modal (Sep 2026: transactional modals "are persistent until dismissed" by the primary action, Cancel, × or Esc; for a passive modal, "Clicking outside the passive modal area will automatically close the modal"). *House defaults.*
- **A form's size and use pick its container:** a short, infrequent task with fewer than five inputs, a modal; more than five inputs, or a task repeated while looking at the information it changes, a slide-over; a long, complex or multi-step task, its own page. Exactly five is left open. No tabs or collapsed sections in a modal or slide-over; a modal that would scroll a long way becomes a slide-over or a page. A modal form focuses its first field and stays open with the errors marked when validation fails; Filament does both. Carbon forms (Aug 2026: "Use a dialog form when dealing with less than five inputs", side panels "for repeated requests for user input which require the user needs to reference the affected information"); Carbon modal (Sep 2026: "short and non-frequent tasks"; focus; validation; max heights); Carbon dialogs (Aug 2026: "Don't recreate a full app or page in a dialog"; avoid accordions and tabs); USWDS modal (no complex forms in modals). *Pattern `forms-form-container`.*
- **A wizard is only for a linear task of three or more steps,** not for steps done in any order or whose number depends on earlier answers. Each step is named in one or two words saying what it does ("Set terms"), of at most 16 characters, and has a description only to say it is optional, is checked before the next, and Back returns to review; the last button names the final action ("Create"). Filament's wizard does all but the names. Carbon progress indicator (Sep 2026: "three or more steps"; "When the process may be completed in any order" is a when-not-to-use; labels "in one or two words"); Carbon forms (Aug 2026: multistep forms let users "return to a previous step to review"); Carbon modal (Sep 2026: "the Next button label should change to reflect the final action"). Carbon progress indicator (Sep 2026: "a limit of 16 characters total per label"). *Pattern `forms-form-container.wizard`, test (label length).*
- **One primary action per screen; the rest are gray or in "…".** Carbon button (Sep 2026). *Audit.*
- **In a modal or slide-over, Cancel is on the left and the primary button on the right; a full-page form keeps its primary first, on the left.** Filament orders them so only when the footer is centred, which also keeps the keyboard order the same as the order on screen (WCAG 2.4.3). Carbon modal (Sep 2026: "the secondary button is on the left and the primary button is placed on the right"); Carbon dialogs (Aug 2026: "Cancel is always the outmost left button option"); Carbon button (Sep 2026: on full-page designs the primary "will be left-aligned"). *House defaults.*
- **A form modal keeps its header and buttons in view while its fields scroll, and never scrolls sideways;** a wide table goes in a wider modal, a slide-over or a page. Carbon modal (Sep 2026: "the body section should scroll vertically with the header and footer remaining fixed"; "Modal content should never scroll horizontally"). *House defaults (sticky header and footer).*
- **A modal opens only when the user asks for it, never on page load, and never opens another modal,** except a message that is critical and needs action at once, such as a session about to end (Carbon notifications pattern, Aug 2026: "Only use a modal when the message is critical and needs the user's immediate attention or action"; "Only display one modal notification at a time"). **It has no links that leave it, and a table in it is only for choosing.** So no `createOptionForm()`, `editOptionForm()` or `ModalTableSelect` in a modal form, and no confirmation on an action inside one. Carbon modal (Sep 2026: "Modals are triggered as a result of a user's action"); Carbon dialogs (Aug 2026: "One modal should never trigger another modal"; "Avoid components like links that will take the user away"; no batch actions "inside the modal itself").
- **A page header shows at most three buttons, all one size; the rest go in a labelled menu button that ends with a chevron.** The icon-only "…" menu is for table rows and cards. A menu holds at most 12 items, a labelled menu button fewer than five; the items don't repeat the button's verb ("New" → "Supplier"), and Delete, Void or Remove comes last, below a divider. Carbon button (Sep 2026: "Any more than three actions should be grouped meaningfully using menu buttons"; "We do not recommend mixing different button sizes"); Carbon menu buttons (Sep 2026: the icon "should always be a caret"; "The shared action should not be repeated"); Carbon menu (Sep 2026: "no more than 12 items"; "under 5 items"; a divider before actions "such as deleting"). *Audit (header buttons), house defaults (chevron).*
- **Every icon-only button has a tooltip naming what it does, shown on hover and focus;** a tooltip that defines or instructs is a full sentence. Carbon tooltip (Sep 2026: "Every icon-only button needs a tooltip"; "write the text as complete sentences with punctuation"). *House defaults (the "…" menu), test, audit (`->tooltip()` on an icon-only action).*
- **No menu or dropdown opens inside another; a dropdown holding fields is at most 352px wide, and none holds critical information or required input.** A nested `ActionGroup` is `->dropdown(false)`, so its actions sit in the outer menu under a divider. Carbon disclosures (Aug 2026: "Do not nest one disclosure within another disclosure"; "Don't use to present critical information or request required input"); Carbon popover (Sep 2026: "Avoid nesting popovers"; wider than four columns, "use a modal instead"). Nested menus also fail axe's ARIA and target-size checks. *Test.*

### Approvals

Pattern `actions-approve-and-reject`. Checked against the live sources on 2026-10-11; Carbon has no approval pattern, so these rules apply its button, dialog and disabled-state guidance.

- **Approve and Reject show only while the record waits for a decision, and only to users who may decide** (a policy method); otherwise they are hidden, not disabled. Carbon disabled states (Aug 2026: hidden when the user "does not have permission"). *Pattern.*
- **Approve is the page's one primary button; Reject is secondary (gray), the negative action of the pair, never danger,** because nothing is destroyed. Carbon button (Sep 2026: secondary is "the negative action of the set"; danger is "for actions that could have destructive effects"); Carbon action labels (archived: Approve "typically initiates the next step", Reject "typically blocks the process from proceeding"). *Pattern.*
- **Approve posts the document, so it confirms in the same danger dialog as Post,** saying the document gets its number and can no longer be changed; each decision ends with a toast naming the outcome ("Order PO-000042 approved"). See "Confirm destructive or irreversible actions" and Notifications. *Pattern.*
- **Rejecting always asks for a reason and returns the document to Draft,** where the reason shows until it is sent again. For approval is blue, beside Draft, Posted and Void (see Documents). Carbon status indicators (Aug 2026: blue for "workflow progress"); the lifecycle is a business standard (see Business standards). *Pattern, `tables-status-badge`.*

### Notifications

Pattern `feedback-notifications`. Checked against the live sources on 2026-10-11: Carbon notification usage and accessibility (Sep 2026), notifications pattern (Aug 2026).

- **The kind follows what the message is about.** A toast says how something the user just did went (saved, deleted, sent); it slides in at the top right and needs no reply. An inline notification is about part of the page: it sits at the top of that part, never covers content, and stays until the issue is resolved; in Filament it is a `Callout`, info or warning only, never success or danger, just above the field or button it concerns, and used sparingly. A `Callout` isn't announced to screen readers, so it is only for a message that is there when the page loads; feedback on something the user just did is a toast, or a `Callout` with `role="status"`. Carbon notification (Sep 2026: the callout variant "only includes informational and warning statuses"; "place the callout above the relevant button or input"); Carbon notification component docs (React, Oct 2026: a callout "will not be announced to screenreader users" and is not for "notifications responding to user input"); WCAG 4.1.3. Something the user must decide before going on is a dialog (see "Confirm destructive …"). *Test (success or danger callout).* Carbon notification usage (variants: inline, toast, actionable, callout) and notifications pattern (modal notifications are for "critical information that needs their attention or action"). *Pattern.* Save feedback stays a toast; see "Not adopted from Carbon".
- **Colour follows the outcome:** success for a task completed as expected, warning for something done that may have unexpected results, danger for an error or failure, info for something not tied to the current task. Carbon notification usage and notifications pattern (status table). *Pattern.*
- **The title is short, says the most important thing, and has no full stop; after a failure it says what stopped or wasn't done** ("Abra Medical Supply not saved"). **The body is one or two short sentences that don't repeat the title; after a failure it says how to fix it.** Plain words, no technical jargon. Filament's own titles ("Saved", "Created", "Deleted") meet this; naming the record is allowed, not required. A toast's body fits in two lines at its 288px width; a longer message gets one "View more" action (Carbon notification, Sep 2026: "limit toast notifications to two lines of text"). Carbon notification usage (Content: "Don't use a period to end a title"; "User actions are mandatory for error messages"); notifications pattern ("Do not use technical jargon"); Carbon inline loading (Sep 2026: "Saved"). *Test (full stop), pattern.*
- **At most one action in a notification, of one or two words, and optional:** it never blocks the user, and usually takes them where they can resolve the message. What it leads to can also be reached another way, since a toast can vanish. Carbon notification usage ("Only one action is allowed for each notification"; "Limit action labels to one or two words"; "ensure there are alternative routes"); notifications pattern ("should not block the user"). *Pattern.*
- **A toast without an action may close itself after a few seconds,** and always has a close button. **A toast with an action, and an error, stays until the user dismisses it.** What a timed toast said can be found again afterwards, on the record or the list. Filament's 6 seconds conforms: Carbon's toast "can timeout and be coded to dismiss automatically after five seconds", and no qualifying source sets a number. Carbon notification usage ("the notification should remain on screen until the user dismisses it", for an actionable toast; "users should be able to access them elsewhere"); notifications pattern ("Don't use notifications that dismiss on a timer for critical or emergency messages"; error means "an error or critical failure"). *House defaults.*
- **The same database notification isn't sent again while the first is unread, and work that takes more than a few seconds runs queued and ends with a notification,** as imports do. Carbon notifications pattern (Aug 2026: "Don't send the same notification multiple times if users don't interact with it"); Carbon loading pattern (Aug 2026: "consider including a notification").
- **The notifications panel (Filament's bell) lists every notification newest first, unread ones marked, with Mark all as read; the bell's name gives the unread count, and the empty panel says what will appear in it.** Filament does the rest; the house defaults word the empty panel and keep the 288px toast width out of the panel. Carbon notifications pattern (Aug 2026: panels "ensure that users can access and read all notifications"; "List notifications in chronological order"); Carbon empty states. *House defaults, house CSS.*
- **Screen readers announce a notification without it taking focus:** `role="status"`, and `role="alert"` for an error. Filament's toasts already do. WCAG 4.1.3 (May 2026); Carbon notification accessibility ("Use the roles alert, log, or status for notifications that do not require user action").

## Writing

Labels, headings, buttons, helper text, empty states, notifications and errors. Error messages and helper text follow GOV.UK (see Forms); the rest follows Carbon. Marketing and long-form guidance doesn't apply.

- **Sentence case for labels, headings, buttons, column titles, tabs, badges and notification titles:** a capital only for the first word, names, product names and acronyms (TIN, VAT). Carbon content (Sep 2026: "Use sentence-style capitalization for headings, titles, labels, banners, and similar elements"); Carbon forms (Aug 2026: "except for product names and proper nouns"); Carbon data table (Sep 2026: "Column titles should use sentence-case capitalization"); Carbon button (Sep 2026: "sentence case for all button labels"). Filament writes its own labels in sentence case, but title-cases the model in some modal headings ("Delete selected Purchase Orders"), which the house defaults correct, and in every resource's Create page title ("Create Supplier"), List page title, navigation and breadcrumbs, which a plugin can't reach. A resource fixes them with `use Josephdlmd\FilamentStorybook\Concerns\HasSentenceCaseLabels;` and a `$recordTitleAttribute`; one whose records have no name sets its List page's `$title` and its `$breadcrumb` instead. *Audit, test, house defaults (modal headings).*
- **Italic only for a title of a work or a technical term inside a sentence,** never a whole value or column. Carbon typography (Sep 2026: italic "should only be used when you need to emphasize certain words in a sentence").
- **A label is one to three words that say what to enter, with no colon; a column title is one or two words.** Carbon forms (Aug 2026: "Use one to three words only"; "Do not use colons after label names"); Carbon text input (Sep 2026); Carbon data table (Sep 2026). *Audit (colons).*
- **Plain words the user would use: no technical jargon and no internal codes.** Carbon notifications pattern (Aug 2026: "Do not use technical jargon or language unfamiliar to the user"); Carbon empty states (Aug 2026: "plain language (no codes)").
- **An icon-only button's name is one or two words saying what it does.** Carbon tooltip (Sep 2026: "a concise one- or two-word description of the button's function"). See also the accessibility floor.
- **The same function has the same label and icon on every page, and help and navigation stay in the same place.** IBM Accessibility content design (2026: "Across related content, use the same labels and icons to represent the same functions"; "Provide navigation mechanisms in the same order on all pages"); WCAG 3.2.3 and 3.2.4; WCAG 3.2.6 (Understanding, Mar 2026: help repeated on several pages, such as a contact link or a help page, "occur[s] in the same order relative to other page content").

## Tables and finding

- **A readable identifier comes first; the other columns follow in order of importance and are easy to hide** (`toggleable()`, with the column manager's Reset bringing back the default), **but are not reordered,** since Filament reorders columns only by dragging. NN/g data tables (Apr 2022); WCAG 2.5.7. *Audit (`reorderableColumns()`), pattern `tables-list-table`.*
- **Amounts and other numbers that can be totalled are right-aligned; phone numbers, postcodes, dates and IDs are not.** USWDS table (Aug 2026: "Right-align numerical data"). Carbon is silent. *Audit, pattern `tables-money-column`.*
- **A state shown as an icon alone is only a yes or no, as a tick or a cross,** never colour alone and at 3:1; a status with more than two values, or one that needs action, is a badge with its word, and one that needs no attention is plain text. Filament already gives each icon text for screen readers. Carbon status indicators (Aug 2026: icon indicators "require an icon, a shape, a meaningful color, and a descriptive inline label"; "rely on at least two of the following elements: color, shape, or symbol"; "Avoid using status indicators when no user action is required"); WCAG 1.4.1 and 1.4.11.
- **Editing a row while looking at the table happens in a slide-over, not in the cells.** Carbon sets no rule on editing in a cell; if a cell is editable (`TextInputColumn`, `SelectColumn`, `CheckboxColumn`), it works by keyboard as any field does, and the house script names it after its row ("Quantity, C-0001"). Carbon forms (Aug 2026: a side panel "for repeated requests for user input which require the user needs to reference the affected information"; "Carbon does not have consolidated guidance around inline editing"); Carbon data table accessibility ("inputs … inside tables operate by keyboard as normal"). *House script.*
- **Column groups (`ColumnGroup`) are one level deep; a table needing more is split.** Filament marks them `scope="colgroup"`. W3C WAI multi-level headers tutorial (2019: "consider … restructure the information in such tables to make them less complex").
- **One search field in the table's toolbar, whose placeholder says what it searches** ("Search by code or name"). Carbon data table (Sep 2026) and search (Aug 2026: placeholder text "hinting at what the user can search for"). A search field's placeholder is not a form field's (see Forms). *Pattern `tables-list-table`.*
- **No search on a list that stays short,** such as a record's lines or a fixed lookup; global search's placeholder says what it searches, as a table's does. Carbon search (Aug 2026: "Do not use when there is small or limited amounts of data").
- **With more than one filter category, filters sit above the table or on its left, never in a menu or dropdown.** They apply as they change, with an Apply button only when results are slow, and have a way to clear them all. Carbon filtering (Aug 2026: "horizontally at the top of the data set"). In Filament that is `FiltersLayout::AboveContent` with `deferFilters(false)`; the collapsible layout puts its button alone in a row above the search, with a count even when no filter applies. A yes-or-no filter's empty choice says "All", as a select filter's does. A date range is one filter with From and To side by side (Carbon date picker: range inputs "with a start and end label"), either left empty, each shown as its own indicator. *Audit, test, house defaults ("All"), pattern `tables-list-table`.*
- **An advanced filter (`QueryBuilder`) applies on an explicit action, and the closed filter shows how many filters are applied with a way to clear them;** no source says when to offer one. Carbon filtering (Aug 2026: the batch filter "works best when the user is making several filtering selections across different categories"; "At a minimum, the indicator should include the number of filters applied and have the option to clear filters").
- **Applied filters stay applied for the rest of the session, until the user clears them.** Carbon search (Aug 2026): a selected filter "should persist during future searches until the user either discards the filter or begins a new session". The search and the sort stay too (`persistSearchInSession()`, `persistSortInSession()`). Carbon global header (Aug 2026: "Maintaining these states and filters will bring the user back to where they were"). A filter starts with none or all of its options, never a subset, and a multiple-choice filter has no select-all (Carbon filtering: "start either as all unselected or all selected"; Carbon dropdown). *Pattern `tables-list-table`.*
- **Import and export sit in the List page's header, gray beside the primary New button.** Carbon data table (Sep 2026: the toolbar holds "global table actions such as … exporting"); Carbon button (Sep 2026: a ghost button "if there is another button on the page that requires primary styling"). *Pattern `tables-import-and-export`.*
- **An import says what it accepts before the upload** (a CSV file, its columns, with an example file to download, and the most rows) **and checks each row with the form's own rules and error wording, on the server.** Rows that fail are skipped, and the notification when the import finishes says how many and offers the errors to download, fix and import again. USWDS file input (Aug 2026: state limits up front); Carbon notification usage (Sep 2026: "User actions are mandatory for error messages"); error wording as in Forms. *Pattern, house defaults (the row limit is stated; wording).*
- **Key columns are sortable.** NN/g data tables (Apr 2022); USWDS table (Aug 2026).

## Dashboards

Pattern `dashboards-key-figures-and-charts`. Checked against the live sources on 2026-10-11. Carbon's data-visualisation pages show no update date; the dates are their sitemap entries (Sep 2026), and several are marked a work in progress.

- **Most important first:** key figures at the top, then charts, then the rest, and only what helps the user decide where to look. Carbon dashboards ("Place the most important at the top of the page"; "Limit the number of metrics"). The most important widget also takes the widest span. Key figures sit two or four across, never in thirds, which Filament uses for three figures; the stats in one widget are all links or none. Carbon dashboards ("The most important data should have the highest contrast and occupy the largest area"); Carbon 2x grid (Sep 2026: "divide by two"); Carbon tile (Sep 2026: "Do not mix different variants of tiles in groups"). *Pattern.*
- **A key figure is a number with a short label,** in the app's locale and with its unit (₱ for money). A change has a + or − sign or an up or down arrow (`descriptionIcon()`) and says it in words ("3 more than last week"), never by colour alone; green and red by sign are allowed, not required. A sparkline is decoration, so its trend is also in the description. Carbon chart anatomy ("a number with a single word description"); Carbon status indicators (Aug 2026: a differential indicator "must have either a '+' or '-' sign, a caret, or an arrow icon"); WCAG 1.4.1. *Pattern.*
- **A chart's type follows its purpose:** a line for a trend over time, bars to compare values, stacked bars for parts of a whole. Carbon simple charts. A pie or donut chart labels each slice with its share of the whole ("Paid 62%"), and its text values list every slice, including any too small to draw; each slice is labelled or meets 3:1 against its neighbours (WCAG 1.4.11). Carbon chart anatomy (Sep 2026: "In a circular chart, labels offer the percentage value of the whole for an individual category"). *Pattern.*
- **A scatter chart shows a correlation between two measures, and a bubble chart adds a third as the bubble's size.** No source covers radar or polar-area charts, so there is no rule on them. Carbon simple charts (Sep 2026: scatter plots "explore correlations between different measures"; bubble: "The size of the bubble represents the third measure").
- **A chart's heading says what it shows and its description the main insight; one series needs no legend, and several are labelled on the chart where they fit, otherwise with a legend above or below; an axis says what it counts; a bar or area chart's value axis starts at zero; gaps in the data are shown, never joined up; each data set keeps one colour on every chart of the dashboard, and several series each get their own colour from Filament's palette, meeting 3:1 on the light and dark backgrounds, and their own line style (Filament otherwise paints them all one colour); a time axis lists every period in the range (0 for none, `null` for unknown) and gives a new year's first label its year; a gap's start and end are named in the text values; no acronyms in titles, legends or axes; legends sit in one place on every chart; no gradient fills; a legend, where one shows, is not clickable (`'legend' => ['onClick' => null]`), because Chart.js hides a series on a mouse click the keyboard can't make, so charts are filtered with the dashboard's filters.** WCAG 2.1.1 for the legend, decided by the owner on 2026-10-11 (Carbon's legend isolates a series on click). Carbon chart anatomy, legends, axes and labels, dashboards ("Always start numerical axes at zero" for bar and area charts; "Never interpolate between periods when data is unavailable"; "Always use consistent colors for each data set"). Carbon axes and labels ("Never change axis ticks increments to accommodate data availability"; "label both the start and end point"); Carbon legends ("avoid acronyms"); Carbon color palettes ("maximize contrast between neighboring colors"; "Never use a gradient"). *Pattern, audit (a clickable legend, a legend on one series, several series in one colour).*

- **Every chart gives its values as text.** In Filament, `getChartAssistiveContent()`, built from the chart's own data so the two never disagree. WCAG 1.1.1; W3C WAI complex images (Apr 2026: a long description, "a textual representation of the essential information"). *Pattern.*
- **Widgets don't refresh by themselves.** Filament's stats and chart widgets reload every 5 seconds unless `$pollingInterval` is `null`, and the user can't stop them. WCAG 2.2.2 (content that updates itself beside other content can be paused, stopped or hidden). A filter for several charts is a dashboard filter every widget reads (`HasFiltersForm` with `InteractsWithPageFilters`), not a dropdown on each, and a Refresh button, not polling, brings figures up to date. Carbon dashboards ("Mirror chart modifications like filter and zoom"); Carbon common actions (Refresh). *Audit, pattern.*

## Layout and pages

- **Spacing comes from the theme's scale; nothing sets its own padding or margins.** Things that belong together sit closer than things that don't, and space, not a divider, can separate sections; Filament's sections, groups and columns already space this way. Carbon spacing (Sep 2026: a scale in multiples of 2, 4 and 8, used inside and between components; "Deviating from the spacing scales should be avoided whenever possible"; "Elements in a design that are near each other are seen as being meaningfully related"). More space around something gives it more weight, and a page may have dense parts but is never crowded as a whole. Carbon spacing (Sep 2026: "Elements that have more spacing around them tend to be perceived as higher in importance"; "Sections of a UI are allowed to be dense, but the whole page should not be crowded"). *Test (story snippets).*
- **Text sizes, weights and colours come from the theme,** through Filament's `size()`, `weight()` and `color()` options, never a component's own classes or styles. Emphasis is a heavier weight before a bigger size; semibold is for headings, not long text; running text stays neutral. Carbon typography (Sep 2026: "Font weight is an important typographic variable that can add emphasis"; "A bold weight will always have more emphasis than a lighter weight font of the same size"; semibold "should not be used for long text"; "Keep type color neutral in running text"; "Mixing type styles within a component could jumble the hierarchy"); Carbon color usage (Sep 2026: "Hard coded values will not change when the mode is switched"). *Test (story snippets).*
- **A compact app's text follows Carbon's productive type set** (Sep 2026: "The productive type set uses a base type size of 14px"; for product pages with "a higher density of information"). By role:

  | Text | Carbon token | Size, line, weight |
  |---|---|---|
  | Field labels, read-only labels, error messages | label-01 | 12px, 16px, regular |
  | Helper text under a field, a wizard step's description | helper-text-01, label-01 | 12px, 16px, regular |
  | Values, table cells, buttons, links, body text, a single checkbox's or radio's label | body-compact-01 | 14px, regular |
  | Section headings, table headers, menu group headings, notification titles | heading-compact-01 | 14px, semibold |
  | Badges, breadcrumbs | label-01 | 12px, regular |

  Page titles, dialog headings and key figures keep the theme's sizes: Carbon has no page-title token, its dialog heading (heading-03, 20px) is bigger than Filament's, and it sets no size for a key figure. Line heights stay Filament's 20px for 14px text, not Carbon's 18px, so components keep their alignment. A story emphasises a value with `->weight(FontWeight::SemiBold)` and tones down secondary text with `->color('gray')`, never with its own size; `storybook-test` warns on a font size, weight or colour set by class or style. *`compact()`; test (story snippets).*
- **Lists and record pages use the full width.** Carbon 2x grid (Sep 2026): the high-density model for complex product interfaces "uses the full width of the browser". Filament stops content at 1280px. *House defaults (unless the panel sets its own `maxContentWidth()`).*
- **Record pages divide the 16-column grid by two and by four, never in thirds, and stack on a narrow page.** A record's facts are a list of labels and values. Carbon 2x grid (Sep 2026: "divide by two"; it advises against layouts in thirds); Carbon structured list (Sep 2026: "terms and definitions"); WCAG 1.4.10. Anything sticky must never hide focus (WCAG 2.4.11). *Patterns `records-view-page`, `records-details`.*
- **A related list's actions follow what the related records are.** Records that belong only to this one (a supplier's contacts) are made with New and destroyed with Delete. Records that exist on their own (the users in a team) are put in with Add and taken out with Remove, and the Remove dialog says the record stays. The list's button is gray when the page has a primary action. Carbon common actions (Aug 2026: Remove "is distinct from delete, as a removed item is not destroyed"; "Inform the user if the result is permanent"); Carbon button (Sep 2026: a ghost button for table actions "if there is another button on the page that requires primary styling"). *Pattern `records-related-records`, house defaults (Add and Remove labels), audit (labels and confirmations).*
- **Frequently used or critical content, and content users check against the details, is shown on the page, not in tabs.** On a record page that means its related lists. Carbon tabs (Sep 2026): "Do not use when tabs contain frequently used or critical information"; NN/g tabs (Aug 2024). *Audit.*
- **Tabs group different but related content in the same context:** as few as possible, with one- or two-word labels, in one row. Switching formats or filters of the same content is a content switcher, not tabs. Carbon tabs (Sep 2026); NN/g tabs (Aug 2024: "Use Only One Row of Tabs"). A List page's tabs (`getTabs()`) are Carbon's content switcher: noun labels of up to three words, one always selected, the most used first, starting on the left; schema `Tabs` aren't used for that. No tabs for content users compare. Carbon content switcher (Sep 2026: "Label text should be nouns or noun phrases"; "should never be centered"); Carbon tabs (Sep 2026: "should not be used if the user needs to compare information"). *House CSS (left-aligned).*
- **No crucial information or required input in a collapsed section; if users will read or fill all of it, don't collapse it.** NN/g accordions (Jul 2023): "Essential information should be presented outside of accordions"; A collapsible section starts collapsed; one that should start open isn't collapsible. Carbon accordion (Sep 2026: "begin by default in the collapsed state"). *Audit, test.*
- **Pages in a hierarchy deeper than two levels show breadcrumbs; single-level navigation has none.** Breadcrumbs leave out the current page, which Filament always adds, so a List page has none. Carbon breadcrumb (Sep 2026: "By default, the current page is not listed"). *House CSS.*
- **The menu has two levels at most: groups, then their pages.** A page inside a group has no pages under it; they become items of the group, or the page's own sub-navigation. Carbon UI shell left panel (Oct 2026: "does not support three tiers of navigation"); NN/g menu design (Jun 2024: "highly inadvisable for more than two tiers"). *Audit.*
- **Menu groups and items are short, familiar words with the key word first,** in sentence case like every label. USWDS side navigation (Oct 2024: "Keep the navigation links short"); NN/g menu design (Jun 2024: familiar category labels, front-loaded key terms). *Audit (sentence case of groups).*
- **Menu items name places, never actions** ("Suppliers", not "New supplier"), are fixed pages, never one per record, and carry no record counts; groups follow the users' tasks, and a page's own navigation is tabs at the top (`SubNavigationPosition::Top`). Carbon UI shell header (Oct 2026: "Avoid using verbs as header links"); Carbon global header (Aug 2026: no content "that has no upper limit"; "an appropriate domain model rather than an org chart"); Carbon UI shell left panel (Oct 2026: "use tabs within the page"); Carbon status indicators (a number badge only for global actions). *Audit (verbs, counts).*
- **The app keeps Filament's light and dark modes and its switcher, and a logo with a background has a dark-mode version.** Carbon color (Sep 2026: switching modes "is highly encouraged"; no "images with colored backgrounds"). *Audit (dark mode).*
- **Menu icons support the words and never replace them:** the sidebar never shrinks to icons only; to give the page room, it hides whole (`sidebarFullyCollapsibleOnDesktop()`). NN/g menu design (Jun 2024: icons "should be additional supportive elements, rather than replacing clear text labels"). *Audit.*
- **A message that needs action goes at the top of the content area it relates to;** a system-wide message goes directly below the header. Messages are never stacked: combine them into one, with a list of links. Carbon notifications (Aug 2026: "refrain from stacking them together"); USWDS site alert (Jan 2025: "Avoid stacking multiple site alerts").

### Read-only and locked records

Patterns `records-details`, `records-view-page` and `records-locked`. Checked against the live sources on 2026-10-10.

- **A value the user may read but not change is read-only, never disabled.** Read-only text keeps 4.5:1 contrast, stays reachable by keyboard and is read by screen readers. A disabled control is skipped by screen readers and exempt from contrast, so it never holds something the user needs to read. Carbon read-only states (Aug 2026); WCAG 1.4.3 (Sep 2026: the exemption covers controls "not available for user interaction"); WAI-ARIA 1.2 `aria-readonly` (focusable, and copying is supported).
- **Information that can't be edited here is text, not a field.** A View page is an infolist of entries, never Filament's default disabled form. Carbon read-only states: "If the component does not have an enabled state, do not use a read-only state to display static information." *Audit.*
- **Key-value pairs (`KeyValueEntry`) have short column titles, one or two words in sentence case;** no source says when free-form keys beat fixed fields. Carbon structured list (Sep 2026: column titles "sticking to one or two words").
- **Disabled is only for a control that becomes available once the user does something on the same screen.** When it holds up the primary action, an inline notification says how to enable it. Hide what the user may never do. Carbon disabled states (Aug 2026).
- **Read-only fields look read-only:** no field background and a fainter border, with the text at full contrast. Filament's `readOnly()` changes nothing. Carbon read-only states. A read-only field shows the arrow cursor, and a text area grows only in height (Carbon read-only states: "The arrow cursor reinforces that a component is in a read-only state"; Carbon text input). *House CSS.*
- **When the user may not change a record, its values are read-only and its Edit action is hidden.** Carbon read-only states (Aug 2026, Permissions: "A user's credentials allow them to view the component but not modify it"); Carbon disabled states (Aug 2026: hidden when the user "does not have permission to … take action"). *Pattern `records-locked`.*
- **In a partly locked form, the locked fields are read-only.** Choice fields (radios, selects, checkboxes) have no read-only state in Filament, so they show their value as text. Carbon read-only states (Permissions; choice controls have a read-only state there). *Pattern `records-locked`.*
- **When editing is unavailable only for now** (a process running, or another user editing), Edit stays visible but disabled; when that holds up the primary action, an inline notification says how it becomes available. Carbon read-only states (Application process, Locked) and disabled states ("should never fully disappear"); USWDS button (Oct 2024).
- **Which statuses lock a record is a business fact.** Each app sets its own, ideally on its status enum, and uses it in its own `app/Stories`; the shared pattern uses one generic condition on the record.
- **A numbered badge marks new or updated items and clears once they're acknowledged,** with up to three digits. Carbon uses it only on the header's global actions. Carbon status indicators (Aug 2026).
- **Error pages use plain language and keep any error code small; they say what happened and give a way out** (home, contact or search). Carbon empty states (Aug 2026: "plain language (no codes)"); USWDS 404 page (Mar 2023); NN/g error messages (May 2023). A 403 page says who to ask for access (Carbon empty states: "Suggest steps or process to request access").

## Documents

Patterns `forms-document-totals`, `records-document-lifecycle`, `actions-void`, `actions-record-payment`, `records-paper-receipt`, `forms-record-picker` and `actions-download-pdf`. Checked against the live sources on 2026-10-11; Carbon has no document pattern, so these rules apply its modal, button, status and dropdown guidance. The business facts behind them are under Business standards.

- **A document's totals are read-only text under its lines, right-aligned:** the VATable sales, the VAT, the zero-rated and VAT-exempt sales, and the total amount due. They are worked out again on the server when saving, with the same code the form uses, and stored; never taken from the form. Each total's label sits beside its amount, in the right half under the line totals, as on the printed document; stacked on a narrow screen. Carbon text input (Sep 2026: read-only, not disabled, for a value to read); USWDS table (Aug 2026: "Right-align numerical data"); Carbon structured list (Sep 2026: terms and definitions). These are text, not fields, so "labels above fields" doesn't apply. *Pattern `forms-document-totals`.*
- **Posting confirms in a danger dialog, because it can't be undone;** the dialog says the document gets its number and can no longer be changed, and how to correct it (void and reissue). A sales invoice's dialog asks for its form's serial, and the error for one already recorded says what to do. Post is the draft's one primary button and shows only on a draft. Carbon modal (Sep 2026: "If the action is destructive or irreversible, then use a transactional danger modal"; "Both the title and the button should reflect the action"); Carbon action labels (archived: Post "adds status to a log or record"). *Pattern `records-document-lifecycle`.*
- **A posted document has no Edit or Delete;** the policy refuses both, so Filament hides them and the document opens on its View page. A draft may be deleted, confirmed as any delete is. Carbon disabled states (Aug 2026: hide what the user may not do); see "Read-only and locked records". *Pattern `records-document-lifecycle`.*
- **Voiding is low-emphasis danger among the page's actions, confirmed in a danger dialog that asks for the reason,** says the document keeps its number and that this can't be undone, and is shown only to users who may void. While the document has payments, Void stays visible (it becomes available once they are voided, on the same page) and its dialog says what to do first, with nothing to confirm (Carbon modal: a passive modal "presents information the user needs to be aware of"). The verb is Void, not Cancel, because Cancel is the dialog's own button for stopping and closing. Carbon modal and button (Sep 2026); Carbon common actions (Aug 2026: Cancel "stops the current action and closes the component or item"); Carbon disabled states (Aug 2026). *Pattern `actions-void`.*
- **Document statuses:** Draft gray, For approval blue, Posted green, Void red, each with its word, in one status field; a payment status is a field of its own. Carbon status indicators (Aug 2026: gray "indicates drafts", blue for "workflow progress", green "represents normal or success"); red for Void is the owner's business standard, since Carbon sets no colour for it. **Payment statuses:** Unpaid gray, Partly paid blue, Paid green, Overdue red. Carbon status indicators (Aug 2026: gray for "jobs that haven't been started", blue for "workflow progress", red for "danger or error"). *Patterns.*
- **A payment is recorded in a modal, or a slide-over for a collection's six inputs, with the balance due in the amount's helper text, and what it settles is checked against the balance on the server;** the error says the most it can be ("… must be ₱2,363.71 or less, the balance due"). The save locks the document's row and checks again, since two users may pay at once. Carbon forms (Aug 2026: a dialog form for fewer than five inputs, a side panel for more than five); GOV.UK error message (Jan 2024: say the limit, as in "must be 35 characters or less"). *Pattern `actions-record-payment`.*
- **What staff copy onto a paper form is read-only text in the form's own order, each label beside its value (Carbon structured list), each value copyable,** with an amount also in words as it is written on a receipt. Carbon read-only states (Aug 2026: read-only text stays navigable and can be copied). *Pattern `records-paper-receipt`.*
- **A record of its own (a customer, supplier or item) is picked in a searchable select,** on the relationship, searching code and name and showing both ("C-0001 Abra Medical Supply"), opening with the first options in code order. Carbon dropdown (Sep 2026: "Use a combo box when the user needs to select one option, but the list of options may be very long or not predefined"; "The menu opens by clicking anywhere in the field, allowing users to type and sort through the list of options"; options "in alphabetical order"; option text "brief, accurate"). *Audit (a relationship select that can't be searched), pattern `forms-record-picker`.*
- **A posted document prints as a PDF in the one shared layout** (`filament-storybook::documents.print`), from a gray "Download PDF" button on its View page. The PDF is tagged, so its headings and table headers reach screen readers, carries the document's type and number as its title and the app's language, and is A4; text is near-black on white, and amounts are right-aligned. Shown on a phone, the lines scroll sideways in their own box. W3C WCAG 2.2 PDF techniques (PDF6 table headers, PDF9 headings, PDF16 language, PDF18 title, all on a tagged PDF); WCAG 1.4.3; USWDS table (Aug 2026); Carbon action labels (archived: Download "transfers a file from a remote to local"); Carbon button (Sep 2026: one primary action per screen). *Pattern `actions-download-pdf`; test (tagged, A4).*
- **A posted document is emailed from a gray "Email" button beside "Download PDF";** the dialog fills in the billing contact's address, takes an optional message, and says what is sent and from where. Making the PDF takes a few seconds, so the email is queued: a toast says it is on its way and a notification says when it has gone, or that it hasn't and what to do. Carbon button (Sep 2026: one primary action); Carbon notifications pattern (Aug 2026: long work ends with a notification); WCAG 3.3.7. *Pattern `actions-email-document`.*

- **A posted document becomes the next one from its View page's primary button** ("Create order", "Create delivery", "Create invoice"), which makes a draft with the lines copied and opens it, so nothing is typed twice. Creating a delivery is a slide-over of the order's lines with what is left of each, its quantity starting there. On the draft, a copied line's price is read-only and its quantity can only go down; both are checked again on the server. Carbon button (Sep 2026: the next step is the primary action); Carbon forms (Aug 2026: a side panel when the user refers to the affected information); WCAG 3.3.7. *Pattern `actions-create-next-document`, `Fulfilment`.*
- **An order held by its customer's credit limit says why before it is sent:** a warning callout above its buttons gives the amount over the limit, and the primary button is "Send for approval" in place of "Post order"; once sent, its View page shows the reason beside the For approval status. Posting checks the limit again on the server. Carbon notification (Sep 2026: a warning callout "above the relevant button or input"); Carbon button (Sep 2026: one primary action); the approval step in the document lifecycle. *Pattern `actions-credit-limit`.*
## Accessibility floor

- **WCAG 2.2 AA checks on every story and page.** axe-core (its WCAG 2.0, 2.1 and 2.2 A and AA rules), the engine behind Storybook's accessibility addon, on the HTML the server renders, with the theme's CSS and without the page's script: each story; each resource page's content, with each header action's modal open, and a create form submitted empty to show its errors (nothing is saved); and, on a full audit, one whole page, for its title, language, skip link and landmarks. Each is also checked at 320 pixels wide for content cut off or scrolling the page sideways (WCAG 1.4.10). States only script makes (an open menu, a slide-over opened from a row) are checked in a browser. *Test, audit.*
- **Targets at least 24 by 24 CSS pixels.** WCAG 2.5.8. Filament's remove button on a multiple select's badges (20px) and a select's clear button (16px) are made 24px, their glyphs unchanged. *House CSS.*
- **Nothing lost at 320 CSS pixels wide (400% zoom), or with increased text spacing.** A data table may scroll sideways in its own box, which the keyboard can reach; code in running text wraps. WCAG 1.4.10 (a data table is an exception: it needs "two-dimensional layout") and 1.4.12. *Test, audit, house CSS.*
- **Colour never alone:** gray for a draft or not started, blue for in progress, yellow for a warning, green for done, red for danger or error, always with a word. WCAG 1.4.1; Carbon status indicators (Aug 2026). *Pattern `tables-status-badge`.*
- **A colour value shows its text beside its swatch** (a hex code or a name), never a swatch alone; `ColorColumn` and `ColorEntry` show only the swatch on screen, so pair them with the value as text. WCAG 1.4.1 (Understanding, Sep 2025: "requires a visible alternative to color"); Carbon accessibility, color (Sep 2026: "Don't rely on color alone to convey meaning").
- **An image beside text that already names it keeps an empty alt text, as Filament gives it** (an avatar next to the person's name); **an image that carries information of its own gets `->alt()` describing that information.** Carbon accessibility, developers (Sep 2026: "Every image that is not decorative must include alt text … If the image is decorative, use an empty alt attribute"); W3C WAI images tutorial (decorative images are those "Identified and described by surrounding text"); WCAG 1.1.1.
- **Contrast: 4.5:1 for text; 3:1 for status colours against the background and each other, and for chart series against the background and against each other where they touch,** unless labels or values carry the same information. WCAG 1.4.3 and 1.4.11; Carbon status indicators (Aug 2026).
- **Focus is always visible and never fully hidden under the sticky top bar or a sticky aside.** A closed menu is out of the keyboard's reach: Filament slides it off the screen on a phone or tablet but leaves its links in the tab order. WCAG 2.4.7 and 2.4.11. *House CSS.*
- **When the button that opened a dialog is gone** (its row deleted, removed or voided), **focus goes to the same action on the row that took its place, or the last row, or the table,** never to the top of the page. W3C WAI-ARIA APG dialog pattern (2026: when "The invoking element no longer exists … focus is set on another element that provides logical work flow"); WCAG 2.4.3. *House script.*
- **A keyboard shortcut uses Ctrl, ⌘ or Alt** (`keyBindings(['mod+s'])`), never a character key alone, which fires while the user types or dictates. WCAG 2.1.4 (Understanding, Feb 2026: "using only letter … punctuation, number, or symbol characters" needs a way to turn it off, remap it, or act only on focus). *Test, audit.*
- **Tooltips hold only supplementary information; anything needed for the task is visible.** Carbon tooltip (Sep 2026): "do not include pertinent information for the user to complete their task". WCAG 1.4.13 for how they behave.
- **A tooltip sits only on something the keyboard reaches, such as a button: never on a column, an entry or a hint icon,** whose tooltips Filament shows on mouse hover only. Their text goes in `helperText()`, a column's `description()` or the record's page. WCAG 2.1.1; Carbon tooltip (Sep 2026, accessibility: "Users can navigate to the UI trigger and display the tooltip by pressing Tab"); Carbon form (Sep 2026, accessibility: the info icon "is a button, which is in the tab order"). *Test, audit.*
- **A value that can be copied is a button: Tab reaches it, Enter or Space copies it, and "Copied to clipboard" is announced.** Filament's `copyable()` copies on a mouse click only, so the house script makes each one a button named "Copy …". Carbon code snippet (Sep 2026, accessibility: "reachable by Tab and copied with Space or Enter"); WCAG 2.1.1 and 4.1.3. *House script.*
- **A link inside running text is underlined,** in a description, a notification, a callout or helper text; Filament underlines links only on hover. Carbon link (Sep 2026: an inline link "is styled with an underline"); WCAG 1.4.1. *House CSS.*
- **Every icon-only action keeps a `label()`, which becomes its accessible name.** WCAG 4.1.2. *Test, audit.*
- **Row actions are named after their row for screen readers,** "Edit C-0001" rather than every row's "Edit", starting with the visible label; the house script does it, so Filament keeps its fast row rendering. Carbon link (Sep 2026: "Avoid using the same link text for different destinations"); IBM Accessibility content design ("Provide clear, concise, and unique link text"); WCAG 2.4.4 and 2.5.3. *House script.*

## Sign-in

- **"Log in" and "Log out", not Filament's "Sign in" and "Sign out".** Carbon login (Aug 2026: "The title should include the words 'Log in' rather than 'Sign in' or another variant"); GOV.UK has no rule on the label. Decided by the owner on 2026-10-11. *House defaults (translations).*

- **Passwords: at least 15 characters when the password is the only factor (8 when multi-factor sign-in is required); at least 64 allowed; no composition rules; checked against a blocklist of common and breached passwords; pasting and showing the password allowed.** NIST SP 800-63B-4 (Aug 2025; 64, paste and show are SHOULDs); WCAG 3.3.8. The house defaults set Laravel's `Password::defaults()` to the minimum and to `uncompromised()`, which sends Have I Been Pwned only the first 5 characters of the password's hash and lets the password through when the service can't be reached; a new password's field says "At least 15 characters"; Filament already allows pasting and showing it. *House defaults.*
- **A failed log in says "Incorrect email or password. Try again.", the password field is cleared, and "Remember me" says what it remembers.** A new password's helper text states its minimum length. Carbon login (Aug 2026: "Incorrect IBMid or password. Try again."; "the password field cleared"; "Clarify what is being remembered"); Carbon text input. *House defaults (the message).*
- **Multi-factor sign-in offers at least one phishing-resistant option (such as a passkey) and issues recovery codes. Email is never an out-of-band factor;** email recovery codes are allowed. NIST SP 800-63B-4: email "SHALL NOT be used for out-of-band authentication"; at AAL2, "SHALL offer at least one phishing-resistant authentication option"; recovery codes are a SHOULD. Filament 5 has no passkeys, so an app with Filament's authenticator app alone (`AppAuthentication::make()->recoverable()`) meets the recovery codes but not the phishing-resistant option; that needs a passkey package. *Known gap.*
- **A session that ends after a time without activity warns the user 2 minutes before, in a dialog with Stay logged in (primary) and Log out;** Stay logged in, × or Esc keep the session, and activity in any tab of the app counts. A session lasting over 20 hours needs no warning. WCAG 2.2.1 (Understanding, Aug 2026: "warned before time expires and given at least 20 seconds to extend the time limit with a simple action"; "20 Hour Exception"); NIST SP 800-63B-4 (Aug 2025, usability: "Prompt users to perform some activity just before (e.g., two minutes before) an inactivity timeout"). The length is the app's: NIST sets no inactivity timeout at AAL1 ("MAY be applied") and at most 1 hour at AAL2 ("SHOULD be no more than 1 hour"). *House defaults, house script.*
- **New users are invited by email and set their own password; the admin never types or sees it.** The link works for 7 days and once, and sending it again stops the old one; a user still invited shows Invited, or Expired after 7 days, with Send again and Withdraw invitation. NIST SP 800-63B-4 (Aug 2025: passwords are chosen by the subscriber). The 7 days and who may invite (the permission to manage users) are business standards. *Pattern `actions-invite-a-user`, with `UserInvitation` and `AcceptInvitation`.*
- **The account owner is notified when a sign-in method is added or account recovery is used,** and should be when one is removed. NIST SP 800-63B-4. The house defaults email the user when the authenticator app is turned on or off. Filament reports no event when a recovery code is used, so that notice is the app's, in its user model's `saveAppAuthenticationRecoveryCodes()`. *House defaults.*
- **A security code is typed or pasted in any format, with spaces or dashes, and the screens around it follow the writing rules:** a label of a few words ("Security code"), errors that say what to do ("Enter the code your authenticator app shows now"), a confirmation that says the consequence, no links that leave a dialog. GOV.UK confirm a phone number (2026: "Let the user enter the code in whatever format is familiar to them. Allow additional spaces, hyphens and dashes"; "Enter a correct security code"); WCAG 3.3.8. Filament's code boxes take a pasted code; the house defaults reword its two-factor screens. *House defaults (translations).*

## Business standards (from the owner)

Approved by the owner on 2026-10-10.

- **TIN:** the 9-digit TIN plus a 3-digit branch code, stored as `000-000-000-000`, with `000` for the head office. *Pattern `forms-tin`.*
- **Amounts** (prices, totals, payments, balances, VAT and withholding): pesos and centavos, **at most 2 decimal places, checked on the server.** The peso has 100 centavos (PHP; 2 minor units). *Pattern `forms-money-input`.*
- **Unit cost** (weighted-average, landed or derived costs): **up to 4 decimal places,** so costs worked out by division don't drift by centavos. *Pattern `forms-unit-cost`.*
- **Quantity:** **up to 3 decimal places,** for weights, volumes and lengths. *Pattern `forms-quantity`.*
- **Percentages** (discounts, tax rates): **from 0 to 100, up to 2 decimal places,** stored as the percentage itself (12.5 for 12.5%) (owner, 2026-10-12). *Pattern `forms-percentage`.*
- **Phone numbers:** Philippine mobile and landline numbers only, typed any way, **stored as +63 917 123 4567, +63 2 8123 4567 (Metro Manila) or +63 32 123 4567 (provinces)** (owner, 2026-10-12). *Pattern `forms-contact-details.phone`, `PhoneNumber`.*
- **Invitations:** new users are invited by email, never given a password by an admin; an invitation link works for **7 days**; anyone with the permission to manage users may invite (owner, 2026-10-12). *Pattern `actions-invite-a-user`.*
- **Addresses:** Philippine, in separate fields: street address (unit, building, house number and street), barangay (optional), city or municipality, province (optional; Metro Manila has none) and a 4-digit ZIP code (owner, 2026-10-12). A printout joins them into one line. *Pattern `forms-contact-details.address`.*
- **The apps are data-dense** (2026-10-11), like Office apps: Filament's Compact theme tightens controls, cards, modals and gaps, and their tables use Carbon's medium rows, 40px, chosen over small on 2026-10-11 (see Tables). *The Compact theme and `compact()` in each app's panel.*
- **Round once, at the end:** a line total is quantity × unit price, rounded to 2 decimals once, as `forms-line-items` shows. VAT is worked out once per invoice for each VAT class (12%, zero-rated, exempt), on that class's total, then rounded to 2 decimals. This matches BIR's requirement to show VAT as a separate item and to break out taxable, zero-rated and exempt sales (RR 7-2024).
- **Rounding is half up, away from zero for negatives:** ₱50.025 becomes ₱50.03, and a credit of −₱50.025 becomes −₱50.03, so a return mirrors its sale. This is how people check figures by hand and how Excel's `ROUND` and PostgreSQL's `round()` work. Not banker's rounding (half to even). *Pattern `forms-line-items`.*
- **Approval is a step in the document lifecycle, not a lifecycle of its own** (owner, 2026-10-11, replacing the Approved and Rejected statuses decided earlier that day). A document that needs approval (each app says which, such as purchase orders) goes Draft, then For approval (info, blue), then Posted. **Send for approval** takes the place of Post on its draft; while it waits, its figures can't change. **Approve posts it:** it takes its number and locks, as Post does. **Rejecting requires a reason** and returns it to Draft, where the person who raised it sees the reason, changes it and sends it again. Carbon notifications pattern ("Do not leave users without next steps"). *Patterns `actions-approve-and-reject`, `records-document-lifecycle`, `tables-status-badge`.*
- **One method everywhere:** the invoice, the journal entry and the tax returns use the same amounts and the same rounding, so the books always agree with the invoices.
- **Never floating-point money:** money is stored in decimal columns (for example `decimal(15, 2)`, and `decimal(15, 4)` for unit cost) and computed with decimal arithmetic, never PHP floats. Filament hands numbers over as floats, so a value is turned back into its exact decimal string first (`number_format((float) $value, 2, '.', '')`, to its own decimal places) and only then calculated with bcmath; showing an amount (`Number::currency()`, `money()`) may go through a float, since a decimal(15, 2) prints exactly. *Test (`round()` in a story).*

**Documents (approved by the owner on 2026-10-11):**
- **One company,** at one location: no company or branch on any table.
- **Documents:** sales invoices, purchase orders, receiving reports, and payments both ways (collections from customers, payments to suppliers).
- **Statuses:** Draft, then Posted, then Void, with For approval between Draft and Posted for a document that needs approval (above). One status field holds them all; a payment status (Unpaid, Partly paid, Paid, Overdue) is a field of its own. A posted document is never edited and never deleted; to correct one, void it and issue a new one (or a credit or debit note). *Pattern `records-document-lifecycle`.*
- **Voiding** requires a reason, keeps the document's number, and keeps the document visible, marked Void (red). Only users with a void permission (a manager or accountant role) may void; posting doesn't grant it. Who voided it and when are kept. **A document with payments that aren't void can't be voided until they are;** a payment is voided the same way, which gives its amount back to the balance due. *Pattern `actions-void`.*
- **Sales invoices and collection receipts are written by hand on BIR pre-printed forms,** which are the official copies. The app keeps the records (it is not registered as a computerized accounting system), and each is recorded under the serial printed on its form: the user types it when posting, and the app refuses a serial already recorded. One number per document, so the books, the forms and BIR's records agree. Staff copy a collection receipt from its View page. *Patterns `records-document-lifecycle`, `actions-record-payment`, `records-paper-receipt`.*
- **Numbering for the rest:** a prefix for each document type (PO purchase order, RR receiving report, PV payment voucher) and a 6-digit series that never resets, such as PO-000042. The number is given when the document is posted, in the same transaction, with no gaps. *Example `DocumentNumber`.*
- **Prices include VAT.** VAT is 12/112 of each document's VATable total, worked out once and rounded once, half up; the VATable sales are that total less the VAT. *Pattern `forms-document-totals`.*
- **Withholding tax (EWT) applies both ways.** A sales invoice's total amount due is before withholding.
  - **From a customer:** what they withhold depends on who they are, set on the customer: a **government office** withholds 1% income tax and 5% VAT on the VAT-exclusive amount, with no income tax on a single purchase of ₱10,000 or less (RA 10963; the app takes the invoice's total as the purchase until the CPA says otherwise), a **top withholding agent** 1% income tax, others nothing. A collection proposes both and the cash expected (`DocumentTotals::customerRates()`), and the user records what the customer's 2307 shows. Both are recorded with the payment as creditable taxes, even before the 2307 arrives, each with its ATC, and kept apart: the income tax is credited on the income tax return, the VAT withheld (WV010) on the VAT return only, since BIR forfeits VAT withheld claimed on the income tax return (RMC 36-2021; RA 10963). The payment keeps the date the 2307 arrived, and the app lists payments still waiting for one. *Pattern `actions-record-payment`.*
  - **To a supplier:** worked out once, when the supplier's invoice is recorded against the purchase order, since RR 4-2024 makes withholding due when the amount is recorded or the invoice is issued, whichever comes first: the rate of the supplier's ATC (a default on the supplier, changeable on the invoice) on the invoice's total less VAT. Payments settle the net payable. One BIR Form 2307 per purchase order. The supplier's TIN and the ATC are kept with each withholding. WC158 (1% on goods) and WC160 (2% on services) apply only to a company BIR has made a top withholding agent, which the app's `config/company.php` says (`top_withholding_agent`); one of the owner's companies is. Rent, contractors and professional fees have their own ATCs either way, added as the CPA confirms them. *Pattern `forms-document-totals.supplierInvoice`.*
- **A supplier's invoice is recorded as printed:** its total and its VAT as the supplier wrote them, since the printed VAT supports the input tax; the app shows its own figure beside it to catch typing mistakes.
- **A supplier's invoice is recorded on its purchase order,** not as a document of its own (owner, 2026-10-11): the order holds the supplier's invoice number, date and printed figures, its withholding and its payments. *Patterns `forms-document-totals.supplierInvoice`, `records-view-page`.*
- **Payments may be partial;** a payment never settles more than the balance due.
- **Ageing** (statements of account and the ageing report) counts days past the due date, in five buckets: Current, 1–30, 31–60, 61–90 and over 90 days (owner, 2026-10-11).
- **Sending documents** (owner, 2026-10-12): a sales invoice's copy, a purchase order, a payment acknowledgement and a statement of account can be emailed, as the PDF, to the customer's or supplier's billing contact, only when the user clicks Email, from the company's address set on the Settings page. *Pattern `actions-email-document`.*
- **From one document to the next** (owner, 2026-10-12): a quotation becomes an order, an order is delivered on one or more delivery receipts, and each delivery gets one invoice. The next document's lines are copied with their prices, which can't change; a quantity can only go down, to what is left. An order is Not delivered, Partly delivered or Delivered. *Pattern `actions-create-next-document`.*
- **Credit limits** (owner, 2026-10-12): when posting a sales order would take a customer over their credit limit, the order is held: it can't be posted, it goes For approval, and someone with permission approves (posts) it or rejects it. What counts toward the limit is the customer's exposure: unpaid invoice balances, plus posted orders not yet invoiced, plus this order. A customer with no limit set is never held. *Pattern `actions-credit-limit`, `CreditLimit`.*
- **Stock** (owner, 2026-10-12): one warehouse; no lots or expiry dates for now. Stock is valued at weighted average cost: a receipt moves the average, an issue or adjustment goes out at it. Nothing takes an item below zero: posting is refused, saying how many are on hand. An adjustment needs a reason (count correction, damaged, lost, expired) and approval. Each item has its own reorder level; at or below it, the item shows "Low stock". *Patterns `records-stock`, `actions-adjust-stock`, `Stock`.*
- **Reports** (owner, 2026-10-12): sales, collections, receivables ageing, and purchases and payables, each over a date range (the ageing as of a date). Amounts show the VAT-exclusive amount, the VAT and the total in separate columns. Each is on screen, as a PDF and as a CSV or Excel file, for roles with a "view reports" permission. *Patterns `reports-*`.*
- **Statements of account** list the customer's open items: every posted invoice not yet fully paid, by its form serial, with its date, due date, days past due and balance, then the balance in each ageing bucket and the total due (owner, 2026-10-12). *`PrintedDocument::statementOfAccount()`.*
- **A serial is used once:** a unique index on each document's number is the real guard, and a form's check gives the message; the index also catches two users entering the same serial at once. A void document's serial stays used.

**Good business practice, recommended at the owner's request and approved by the owner (2026-10-11):**
1. **When less is received than ordered,** the purchase order stays open, marked Partly received, until the rest arrives or someone who may close orders closes the rest with a reason. For the stock-movement patterns.
2. **Voiding a document with payments:** void the payments first (above), so no payment points at a void document and the 2307s and balances stay right.
3. **Printed copies:** every posted document can be printed from the app as a PDF, except a collection receipt, which is copied onto its paper form. A sales invoice printout is for the business's own file, titled "Sales invoice (copy)", with the form's serial and "This document is not valid for claim of input tax". The copy may also be emailed to the customer (owner, 2026-10-12). For a collection, the customer gets by email a payment acknowledgement, "Payment received (copy)", under the receipt form's serial and marked "This is not an official receipt". Customers also get a statement of account of their open invoices (see Statements of account).
4. **Cancelled paper forms** keep every copy, original and duplicates, intact and marked "Cancelled", with the same reason as the void in the app.
5. **Records are kept at least five years** and posted documents are never deleted. A customer, supplier or item used on a posted document is archived, never deleted; one never used on a document may be deleted for good (owner, 2026-10-12; `actions-archive`). Each customer's TIN and address are recorded, since business invoices need them.

**For the CPA** (questions prepared 2026-10-11): rounding, VAT per document, the supplier's printed VAT, the ATC list, withholding when the invoice is recorded, the creditable withholding recorded before the 2307, and whether the printed copies and the app need BIR registration.

**Decided by the owner (2026-10-10):**
1. **Half up, away from zero for negatives,** as above. No BIR rule setting the method was found; ask the CPA in the same review as item 2.
2. **VAT is worked out per invoice for each VAT class,** not per line. A CPA review is still worthwhile; if the CPA prefers per line, change it here and in the patterns, in one release.
3. **None of the owner's companies is under BIR's e-invoicing (EIS) mandate at present** (RR 11-2025, RMC 98-2026). If one comes under it, EIS's technical specification sets field precision and overrides this section.

## Engineering rules (Filament facts, not UX)

- `Hidden` fields can be edited by the user; set trusted values on the server. (Filament docs)
- A table calls its row actions' closures without a record while it has no rows, so type the record nullable: `fn (?Order $record)`. A closure typed `Order $record` stops the empty list from rendering. (Filament source; three eval agents hit it) *Test.*
- Imports and exports run as queued jobs without policy checks: authorize the actions, and decide in the importer's `resolveRecord()` which records an import may change. (Filament source)
- An imported number stays text and is validated (`numeric`, `decimal:0,2`); `ImportColumn::numeric()` rounds extra decimals away instead of rejecting the row. (Filament source)
- Restrict which records a `ModalTableSelect` offers in `relationship(modifyQueryUsing:)`; the table filter alone isn't a security boundary. (Filament docs)
- Bulk actions check permission per record with `authorizeIndividualRecords()`. (Filament docs)
- No deprecated components: `Select->multiple()`, not `MultiSelect`; `TextEntry`, not `Placeholder`. (Filament 5 source)
- A read-only field is still submitted, and its value can be changed in the browser. Keep locked values out of the save with `saved(false)` on the field or a group around it, and let the policy's `update()` refuse when nothing may change; Filament then hides Edit and refuses the Edit page. (Filament docs) *Audit.*
- A relation manager embedded with `Livewire::make()` skips Filament's `canViewForRecord()` check; keep it with `visible()`, as `records-view-page` shows. (Filament 5 source)
- In Filament, `EditAction::make()` anywhere on a resource page opens the Edit page, or the resource form in a modal when there is no Edit page, and is hidden when the policy refuses `update()`. (Filament 5 source)

## Where we differ from Carbon

- **No placeholder text at all.** Carbon allows it sparingly; GOV.UK and USWDS research shows it disappears, isn't read by some screen readers and is mistaken for a value, and form wording follows GOV.UK.
- **No input masks.** Carbon has no mask component; USWDS's own mask failed WCAG 2.1 AA, and WCAG wins.
- **Truncated text is revealed on focus, on activation or on a linked page, never on hover alone.** Carbon's data table shows it "in a tooltip on hover"; WCAG 1.4.12 Understanding (Oct 2025) counts truncation as passing only with such a mechanism, and WCAG wins.
- **Error messages say what to do ("Enter name").** Carbon's examples state the problem; form wording follows GOV.UK.
- **The menu never shrinks to icons only.** Carbon's left panel offers a side rail that shows only icons until hovered or focused; NN/g menu design (Jun 2024) finds icons "should be additional supportive elements, rather than replacing clear text labels", and the rule follows it.
- **A page form's buttons sit 24px below its last field, not 48px.** Carbon forms (Aug 2026) recommend 48px above the buttons, with 32px between fields; the apps keep the Compact theme's 16px between fields, and at 16px the buttons read as one more field. 24px (`$spacing-06`) is one step more than the gap between fields. Decided by the owner on 2026-10-11, from a side-by-side comparison. *`compact()`.*
- **Helper text has no full stop.** Carbon's text input asks for "full sentences with punctuation"; form wording follows GOV.UK, which asks for "a single short sentence, without any full stops".

## Not adopted from Carbon

Carbon guidance that is no longer published, or that Filament can't follow app-wide (checked 2026-10-11):

- **Carbon's taken-down writing guidance:** second person, present tense, active voice, no "please", contractions, exclamation marks, and spelling out abbreviations. The page was last changed in 2023 and removed on 2026-09-30, and IBM Style, which replaces it, can't be read without a sign-in. IBM Accessibility's content design pages (checked 2026-10-11) don't cover these either: they cover headings, labels, errors, link text, placeholders and consistency, which the rules already follow. Re-check if IBM Style becomes readable.
- **Carbon guidance Filament can't follow app-wide:**
  - feedback on a save shown inline, "in the region of the page the user is working in" (notifications pattern): Filament leaves that region when it saves (Create goes to another page, a modal closes), so it confirms a save in a toast, which is announced as a status message (WCAG 4.1.3)
  - an actionable toast taking focus (Filament has no setting; its toasts stay reachable and are announced)
  - "Move to trash" for a delete that can be restored (Filament's soft delete), keeping "Delete" for the permanent one (Filament's "Force delete"): Filament's delete, restore, force delete and trashed filter would all have to change together
  - "View details" (the archived list only), in place of Filament's "View"
  - Apply rather than "Save changes" (the archived list, for a dialog that stays open; Filament's closes)
  - an inline notification for a server failure in a modal: Filament has no inline slot, and its toast is announced (WCAG 4.1.3)
  - arrow keys between tabs: needs script in Filament, and every tab is reachable by Tab
  - an accordion header named by its title: Filament names its toggle "Collapse" or "Expand"
  - the file's name in FilePond's Remove button, and disabling Cancel while saving: no setting in Filament or FilePond
  - breadcrumbs that never wrap, with an overflow menu: Filament has no breadcrumb overflow menu
- **Carbon details that are its look, not a rule:** 44px touch targets for icons (Carbon's own small components are 32px and 24px; WCAG 2.5.8's 24px stays the floor); icon contrast of 4.5:1 and icons in the text's colour (icon colour is the theme's, and the text beside an icon carries the meaning).
- **Carbon's form spacing on full pages,** 32px between fields and 48px above the buttons (Carbon forms, Aug 2026: "we recommend"), and its 32px gutter between fields side by side, which the 2x grid makes a "MUST" ("Fixed components with labels such as input fields and dropdowns MUST use the wide gutter mode"). The apps are data-dense and keep the Compact theme's spacing, which Carbon allows in modals and side panels ("24px or even 16px"), with 24px above a page form's buttons (see "Where we differ from Carbon"). Decided by the owner on 2026-10-11.

- **Date-range presets** ("Last 7 days", "This month") on a filter, checked 2026-10-12: only product documentation (Shopify, Persona, Siteimprove) recommends them, and Mobbin can only confirm. A date-range filter has From and To, as `tables-list-table.dateRange` shows.

- **Numbers no source sets:**
  - 25 rows per page
  - at most 8 (or 6) columns
  - 3 to 5 figures
  - at most 5 tabs
  - 1/2/3 infolist columns
  - 3 type sizes
  - a pixel type scale of our own (a compact app uses Carbon's productive type set; see Layout and pages)
  - "RelationGroup from four"
  - "CheckboxList up to 15"
- **Input masks.** USWDS's own mask failed WCAG 2.1 AA.
- **Inline labels on forms,** including slide-overs and settings pages. This contradicts labels above fields.
- **Save button on the right on a full-page form.** Carbon puts the primary on the left there; in a modal or slide-over it is on the right (see Feedback and dialogs).
- **Table text or page titles smaller than the theme's** (12px rows, a 20px title) for density. Carbon keeps table text at 14px at every row height; no qualifying source sets a page title's size. Checked on 2026-10-11.
- **The order of menu groups and items, which icon an item gets, and whether every item has one.** Checked on 2026-10-11: Carbon's left panel, USWDS side navigation and NN/g's menu checklist set none of these.
- **How a missing value shows,** whether "—" or a link to where it's added. GOV.UK's summary list links it, but GOV.UK covers form wording, and no qualifying source sets either. An empty section follows Carbon's empty states.
- **Two thirds and one third on record pages** (GOV.UK layout). Carbon's 2x grid advises against layouts in thirds, and GOV.UK covers form wording, not layout.
- **Rules backed only by GOV.UK outside form wording, or by its style guide** (re-checked 2026-10-11):
  - a summary card's actions on its heading row (Carbon has no card pattern)
  - "select", not "click"
  - long forms keep readable line lengths
  - timestamps converted to the user's time zone (Carbon asks only that a time shows its zone)
  - never ISO dates (Carbon shows the international year-month-day format as valid), and a rule on currency symbols and separators
  - error pages say whether work was saved
- **Parts of rules no source sets** (re-checked 2026-10-11):
  - a default sort on every list
  - related lists "most used first"
  - card grids allowed when the records are images
  - "never pre-select a judgement"
  - "about" five inputs (Carbon says five)
  - a count badge meaning waiting work, hidden at zero (the NN/g article cited doesn't say it)
  - a locked record must say why it is locked: Carbon hides an action the user may not take, and asks for a notification only when it is unavailable for now
  - search limited to the identifier (no source limits it)
  - a confirmation heading naming the record or count, and a save message naming the record
  - "offer to clear" filters (Carbon: suggest adjusting them)
  - tabs "never nested", and tabs for "views of the same thing" (Carbon uses a content switcher for that)
  - "warning" meaning waiting (Carbon: yellow is a warning, blue is in progress)
  - tooltips only repeating what's visible (WCAG 1.4.13 doesn't say it; Carbon's tooltip rule replaces it)
  - an authenticator app as the required second factor (NIST asks for a phishing-resistant option)
  - numbered line items, and line-item fields counted to decide a stacked layout
- **Refactoring UI advice no qualifying source backs** (checked 2026-10-11; the book is practitioner advice from 2018). Its spacing, type, colour, contrast, button-emphasis, right-aligned numbers, fewer-borders and empty-state advice is already here on Carbon or WCAG grounds. Not adopted:
